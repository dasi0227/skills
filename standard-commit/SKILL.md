# Git 提交整理

## 权限边界

- 用户只要求分析、规划或生成提交信息时，不要暂存或提交。
- 用户明确要求提交时，可以按本 skill 分批暂存并提交；提交权限不自动包含推送权限。
- 只有用户明确要求“推送”“push”“提交并推送”或“同步到远程仓库”时才执行 `git push`。
- 不要自行执行 `reset --hard`、`clean`、`checkout --`、`stash`、`rebase`、`commit --amend`、强制推送或跳过 Git hooks；确有必要时先说明原因并征得用户同意。

## 拆分原则

### 1. 提交检查

1. 执行 `git status --short` 和 `git diff --stat`。
2. 阅读相关的未暂存、已暂存和未跟踪文件内容；提交信息只能依据实际 diff 编写。
3. 识别用户已有改动，不修改、不丢弃、不覆盖与当前任务无关的内容。
4. 判断改动是否包含多个可以独立说明、验证或回滚的意图，并先形成提交顺序。

> 如果没有可提交的改动，不创建空提交，直接说明当前工作区没有可提交内容。

### 拆分规则

- **按技术模块拆分**：例如前端、后端、脚本、基础设施或独立文件资产。
- **按功能内容拆分**：例如仓库访问、登录认证、文件上传各自形成提交。
- **按需求目标拆分**：例如工具重构与运行时重构分别提交。
- **按变更性质拆分**：新增功能、缺陷修复、重构、性能优化和文档更新互不混杂。

### 拆分约束

- 一个提交只表达一个主要意图；仅仅位于同一目录，不代表必须放在同一提交。
- 实现、直接验证该实现的测试，以及理解该实现所必需的文档或迁移应放在同一提交中。
- 纯格式化、批量重命名或机械迁移尽量与行为改动分开，避免遮蔽核心 diff。
- 每个提交在可行时都应保持可构建、可测试或至少结构完整。

## 提交格式

### 规范

```text
<类型>: <改动概述>

- <用一句话说明实际变动 1>
- <用一句话说明实际变动 2>
```

### 类型

- `feat`：新增或扩展用户、调用方可感知的功能。
- `fix`：修复缺陷、异常行为或不符合预期的结果。
- `refactor`：在不改变外部行为的前提下调整代码结构或职责。
- `perf`：改善运行速度、资源消耗、响应时间或扩展能力。
- `chore`：处理依赖、配置、构建、工具链或其他维护性工作。
- `docs`：只修改文档、注释或示例说明，不改变产品行为。

### 标题

- 使用 `<类型>: <改动概述>`，冒号后保留一个空格。
- 概括该提交最核心的变更方向，不需要罗列正文中的全部细节。
- 使用具体、自然的表述，避免“更新代码”“修复问题”“调整内容”等空泛标题。
- 不以句号结尾，不加入工单号、scope 或破坏性变更标记，除非项目规范或用户明确要求。

### 变动

- 标题后空一行，正文只使用 `- ` 开头的无序列表。
- 每个列表项只用一句话描述一项已经发生的实际变动。
- 不在同一列表项中混合多个无关改动。
- 没有足够内容时使用一个列表项即可，不为凑数量重复标题。

### 示例

```text
feat: 增加文件分片上传能力

- 新增文件分片与并发上传流程
- 保存上传进度以支持中断续传
- 补充分片校验失败时的错误处理
```

## 最终输出

完成分批提交后，只需要按照如下格式输出给用户查看即可，其它内容完全不需要。

```text
已提交到分支 <branch>：
- <短 SHA> 标题
- <短 SHA> 标题
- ...
```
